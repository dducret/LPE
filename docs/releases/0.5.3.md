# LPE 0.5.3

`0.5.3` expands the canonical contact model across the web client, REST API,
JMAP, MAPI, EWS, and ActiveSync.

## Outlook meeting interoperability

- Inbound Outlook meeting requests now resolve Microsoft `VTIMEZONE` STANDARD
  and DAYLIGHT transitions for the event date instead of rejecting zones whose
  winter and summer offsets differ.
- Outlook 2010 and later iMIP discovery searches every `multipart/mixed` child
  for the first non-attachment calendar part; later calendar parts remain
  ordinary attachments.
- Calendar classification parser revision `2` forces previously selected
  calendar parts through the corrected timezone parser; fresh `0.5.2-sql`
  databases ingest the corrected MIME role from the start.
- Outlook can now commit Boolean `PidTagProcessed=TRUE` on an actionable
  Meeting Request. The state is durable per account, idempotent, and visible
  through direct properties, enumeration, CopyTo, and cached-mode sync.
- Server-applied Meeting Responses now use the Calendar Assistant processed
  markers instead of the client-only `PidTagProcessed`. A new-time proposal
  carries its duration, remains non-silent even with an empty body, and
  synchronizes its proposed flag and exact interval onto the organizer's
  attendee row through direct open/read/refresh and cached-mode sync. Calendar
  recipient rows now keep one stable column contract and include the attendee
  response time and matching EX/SMTP SearchKey, so Outlook can correlate the
  response and offer the organizer proposal actions.
- A saved Message retained with `KeepOpenReadWrite` now exposes committed
  recipient replacements immediately to reload, recipient reads, and a second
  edit in the same Execute buffer.
- Meeting Request projection now resolves the logged-on attendee as EX/NSPI,
  keeps unresolved external organizers as SMTP One-Off, and emits
  principal-aware `PidTagReceivedBy*` / `PidTagReceivedRepresenting*` and
  `PidTagMessageToMe` / `PidTagMessageCcMe` / `PidTagMessageRecipientMe`
  properties so Outlook does not classify the attendee as the organizer.
- NSPI `ResolveNames` accepts the protocol-defined array of null-terminated
  Unicode names emitted by Outlook without a private per-string length prefix.

## Contact compatibility

- Contacts now round-trip photos, postal addresses, categories, birthdays,
  anniversaries, children, spouse, assistant details, web pages, and secondary
  email and phone slots through the canonical `contacts` table.
- Contact photo data is stored with its declared content type; postal, web,
  secondary email, and secondary phone values retain their existing structured
  canonical arrays.
- The schema label remains `0.5.2-sql`. This testing-only release directly
  updates the canonical fresh schema; no migration script is supplied.

## Validation

- Protocol contact field behavior is covered by focused storage, JMAP, EWS,
  MAPI, and ActiveSync tests and the web client production build.
